Teaching my Fujifilm X-T30 II to Print on an instax Link 3

2026-11-06

How I added Bluetooth instax printing to a camera that never had it, without flashing anything, with a lot of help from Claude Code

The Problem

I travel with a Fujifilm X-T30 II and a small instax mini Link 3 printer. I like giving prints to people I meet. But the camera can’t talk to the printer. I have to copy the photo to my phone, open the instax app and print from there. That works, but it is slow and it kills the fun.

The X-T30 II can print to instax printers, but only the old Wi-Fi ones (SP-1, SP-2, SP-3). The Link 3 only does Bluetooth LE. Fujifilm added Link support to newer cameras like the X-S10, never to mine. It is on its latest firmware, so no update is coming.

So the only way was to change the firmware. I had never looked at camera firmware before.

Rule zero: don’t brick the camera

Before anything, I set a few rules. A bricked camera is an expensive paperweight, and people in the community have bricked bodies by poking at random memory addresses.

  • Never write to the flash. Everything runs in RAM, and pulling the battery brings back the stock camera.
  • Every write to the camera needs my explicit OK, and the original bytes are checked first.
  • Prefer reading files on the Mac over probing the camera.
  • Don’t waste film. An instax sheet costs about a euro. Debug cards never print.

These rules shaped the whole project. They made it slower, but I never had a moment of panic.

Step 1: Opening the firmware

Fujifilm publishes firmware updates on its website. It’s one .DAT file per camera. The format isn’t documented, but FujiHack had already done part of the work on older bodies.

Opening it took three steps. First, cut a header (model ID, version, checksums). Second, flip every bit (yes, the “encryption” is a NOT). Third, decompress four blocks packed with a custom LZ variant. I wrote a small Python unpacker, fujifw.py, and checked it against zlib tables hidden in the data: if they decode, the decompressor is right.

Three blocks are ARM code: a Cortex-A7 running ThreadX, a small real-time OS. To load them in Ghidra, I needed their addresses in memory. I matched pointers in the code with the positions of the strings they should point to, and the addresses came out. Ghidra then found about 59,000 functions. I ran it headless from scripts, so Claude could ask it for decompiled functions without me clicking around.

Step 2: The code was already there

59,000 functions with no names is a lot. But I had a trick: the X-S10 uses the same processor and does print to Link printers. So I unpacked its firmware too and compared the two.

I wrote a fuzzy matcher. It compares whole functions and ignores the addresses that change between builds. Then I ran it on the 176 functions of the X-S10 print code. 109 of them had a twin in my camera that was at least 90% identical.

That was the big surprise: the X-T30 II already contains Fujifilm’s Bluetooth print app. Cropping, rotation, JPEG encoding, progress screens, everything. Only the bottom layer, the part that talks to the printer over Bluetooth, had been compiled out and replaced by empty functions that return 0.

Even better, the camera already has a Bluetooth LE stack in central mode. It uses it for the Fujifilm Bluetooth grip. So I didn’t need a Bluetooth stack, just the missing glue.

One more detail found here: the print app identifies printers by the first digit of their serial number. My camera knows 1 and 2. The Link 3’s serial starts with 7. Without a patch, the camera would say “unknown printer” even with perfect Bluetooth.

Step 3: Writing the missing piece

The instax Link protocol is well known thanks to people who sniffed it from the phone app: javl/InstaxBLE, linssenste/instax-link-web and others. It’s simple. Each packet starts with Ab, then a length, an opcode, a payload and a checksum. The camera asks a few questions, sends the JPEG in 900-byte chunks and says “print”.

I didn’t copy the X-S10 code. Moving it to another firmware would mean fixing hundreds of addresses. Instead, Claude and I wrote a small C module from scratch, linkxt. It sits exactly where the stubs were: the Fuji app calls it, and it calls the Fuji Bluetooth stack.

The hard constraint was space. The only safe place I found was a 4 KB hole full of zeros in the code, so linkxt had to fit in 4048 bytes. That includes a debug build with logging. Most debugging sessions started with “what can I remove to make room for this new trace?”.

Before touching the camera, every build ran in an emulator. I used Unicorn to run the real ARM binary with a fake Link 3 printer written in Python. It caught a lot of bugs at zero cost.

Step 4: Running it without flashing

Now, how do you run modified firmware without flashing it?

The answer came from jitl and the FujiMod project, found on the FujiHack Discord. Fujifilm cameras can boot from the SD card if you hold a secret button combo at power-on (on mine: Delete + press the rear dial). The card holds a tiny loader, ffinit.bin, and ffboot.bin, an image of the whole RAM (72 MB) built from the official firmware. The camera loads it into RAM and runs it. The flash is never touched.

This was proven on the X-S10, not on the X-T30 II. Getting it to boot on mine took about 30 trials and a lot of black screens. With no screen and no debugger, my only output was the camera’s LED. I wrote loaders that blink green for each stage reached and red for errors, then counted blinks. Later I wrote raw sectors to the SD card from the loader to keep a small log.

The cause, found by reading the code: just before starting the app, the kernel wipes a 128 KB log buffer. That buffer is exactly where my hooks lived. Switching to jitl’s other boot recipe (“cold” instead of “startup”) fixed it. On trial 30, the camera booted from the card to a normal live view. On trial 32, my first mod ran: it turned the LED red for 10 seconds and then let the camera boot.

(I also spent a few evenings on a USB “service mode” route that can read and write RAM live. It was great for checking my RAM image against the real thing, but useless for running code.)

Step 5: Debugging blind

Once linkxt was on the card, the camera showed a new screen: “connecting”… then “CAN NOT BE CONNECTED”. No details.

I needed logs. In the firmware, I found the function Fuji uses to write A:\UILOG\COUNTER.TXT to the SD card, and I reused it. From then on, linkxt wrote everything it did to A:\LINKXT.TXT. Each trial became the same loop:

The logs moved things forward fast:

  • Trials 34-36: scan, connect, find the instax service, enable notifications. Bluetooth works.
  • Trial 37: the first question gets an answer, but the Fuji app rejects it. The Link 3 answers in a newer layout than the old printers. A small shim in linkxt rewrites the answer.
  • Trial 38: all the questions pass and the photo upload starts.
  • Trial 39: the Link 3 accepts a print. The film counter goes from 7 to 6!

The pink ghost

Trial 39 printed. The sheet came out white and slowly developed into… an almost white picture with a faint pink boat. Not quite what I was hoping for.

Since prints cost money, I switched to “no-print” cards. They do everything, but instead of sending the JPEG they save it to the SD card and stop. The JPEG was garbage: pink, zoomed 2×, with stripes on every other column.

I first suspected my code, then the file size, then the source image (an S-size JPEG gave the same result). None of that was it. So I made linkxt dump the image buffers between each step of Fuji’s pipeline, then decoded them on the Mac.

  • After resize: a perfect image, in a YUV layout (“Y Y U V”).
  • After rotation: not YUV at all, but 32-bit ARGB pixels.

Reading the code around it explained everything. Some printers advertise a “capability bit 3”. When it’s set, the app runs an extra colour pass: YUV to ARGB, colour tweak, back to YUV. Then a copy meant for the case without the colour pass runs anyway and overwrites the clean result with half of the ARGB buffer. The encoder reads ARGB as if it were YUV, and you get a pink ghost.

It looks like a real Fujifilm bug. Maybe no printer ever set that bit for this code path, and the Link 3 is the first. The fix is one line in linkxt: hide bit 3 from the app. Trial 45, still without film, gave a clean JPEG.

It works!

Trial 46: real card, real film. Photo picked in the playback menu, “Print”, a progress bar, and the Link 3 starts whirring. A few minutes later, the boat appears.

No phone, no bridge, no flash. Pull the card and the camera is stock again.

javl/InstaxBLE, linssenste/instax-link-web the instax Link protocol

Lessons Learned

Look for code that is already there. I expected to port a whole Bluetooth print feature. In the end I wrote 3 KB of glue, because Fuji had left most of it in my camera.

Compare with a sibling. The X-S10 firmware was my Rosetta Stone. Same chip, same libraries, with names and code paths my camera had lost.

Find a way to log, whatever it costs. An LED, raw SD sectors, then a real text file. Every step up in visibility made debugging 10× faster.

Dump the data, don’t guess. I had five wrong theories about the pink image. One buffer dump settled it.

Don’t debug with film. No-print builds saved me a lot of sheets.

What’s next

It’s still a debug build, and landscape photos haven’t been tested since the fix (before it, they froze on “Sending”). Next, I want to clean it up and turn linkxt into a proper FujiMod mod, so other X-T30 II owners can try it.

Now if you’ll excuse me, I have a Link 3 to fill up.
