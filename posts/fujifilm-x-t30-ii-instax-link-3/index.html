Teaching my Fujifilm X-T30 II to Print on an instax Link 3

2026-11-06

How I added Bluetooth instax printing to a camera that never had it, without flashing anything, with a lot of help from Claude Code

The Problem

I travel with a Fujifilm X-T30 II and a small instax mini Link 3 printer, which I bought during a trip to China. I like giving prints to people I meet, or slipping them into postcards. I also like to travel with my phone out of my pocket as much as I can. But today the phone is the middleman: copy the photo to it, open the instax app, print from there. It works, but it is slow and it kills the fun.

Naively, I thought a fairly recent Fujifilm camera would print to it natively. I had even seen the “instax printer print” entry in the menus. It doesn’t. The X-T30 II only knows the old Wi-Fi printers (SP-1, SP-2, SP-3). The newer ones, like the Link 3, use a new protocol over Bluetooth LE. Fujifilm added it to newer cameras like the X-S10, never to mine. It is on its latest firmware, so no update is coming.

So the only way was to change the firmware. I had never looked at camera firmware before.

Rule zero: don’t brick the camera

Before anything, I set a few rules. A bricked camera is an expensive paperweight, and people in the community have bricked bodies by poking at random memory addresses.

  • Never write to the flash. Everything runs in RAM, and pulling the battery brings back the stock camera.
  • Every write to the camera needs my explicit OK, and the original bytes are checked first.
  • Prefer reading files on the Mac over probing the camera.
  • Don’t waste film. An instax sheet costs about a euro.

These rules shaped the whole project. They made it slower, but I never had a moment of panic.

Step 1: Opening the firmware

Fujifilm publishes firmware updates on its website. It’s one .DAT file per camera. The format isn’t documented, but FujiHack had already done part of the work on older bodies.

Unpacking it took three steps:

  1. Cut the header. The first bytes are an ID card: camera model, version, checksums. The code comes after.
  2. Flip every bit. Every 0 becomes a 1 and every 1 a 0. That’s all the “encryption” there is.
  3. Decompress. What’s left is four compressed blocks. Fuji uses its own flavour of LZ, the classic trick behind ZIP: when a sequence of bytes repeats, it isn’t stored again but replaced by “copy 20 bytes from 300 bytes back”.

I wrote a small Python script, fujifw.py, that does the three steps. To check it, I had a free test: the firmware contains some well-known data tables from zlib, a public compression library. If they come out byte for byte identical to the published ones, the decompression is right.

Three of the blocks are machine code for the camera’s processor (an ARM Cortex-A7 running ThreadX, a small real-time OS). Machine code is just bytes; to read it I used Ghidra, a free reverse engineering tool released by the NSA. You give it a binary, it finds the functions, turns the bytes into assembly and then into readable C-like code. No names, no comments, but readable.

Ghidra first needs to know where each block lives in the camera’s memory. The firmware doesn’t say, so I found it out: the code is full of pointers to text messages, and there is only one address where they all land on the right strings. Ghidra then found about 59,000 functions. I ran it from scripts, without its interface, so Claude could ask it for any function directly.

Step 2: The code was already there

59,000 functions with no names is a lot. But I had a trick: the X-S10 uses the same processor and does print to Link printers. So I unpacked its firmware too and compared the two.

I wrote a fuzzy matcher. It compares whole functions and ignores the addresses that change between builds. Then I ran it on the 176 functions of the X-S10 print code. 109 of them had a twin in my camera that was at least 90% identical.

That was the big surprise: the X-T30 II already contains Fujifilm’s Bluetooth print app. Cropping, rotation, JPEG encoding, progress screens, everything. Only the bottom layer, the part that talks to the printer over Bluetooth, had been compiled out and replaced by empty functions that return 0.

Even better, the camera already knows how to drive a Bluetooth device. Bluetooth LE (Low Energy) is the low-power flavour of Bluetooth used by watches, sensors and printers like the Link 3. In every connection one side is the central, which scans, connects and gives orders, and the other is the peripheral, which waits and answers. Usually the camera is a peripheral: the phone app connects to it. To print, it has to be the central and go get the printer.

The X-T30 II already plays that role in one case: Fujifilm’s Bluetooth shooting grip (most likely the TG-BT1), a small tripod handle with a shutter button that sends commands to the camera. The firmware has a module that looks for the grip and connects to it as a central. So I didn’t need to write a Bluetooth stack, just the missing glue.

One more detail found here. Before printing, the app needs to know which film is loaded, because a mini and a wide print don’t have the same size or shape. It doesn’t ask the printer directly: it reads its serial number and looks at the first digit. 1 means mini, 2 means wide, anything else means “unknown printer, stop”. That list was written for the printers that existed when the code was written. The X-S10, a bit newer, also accepts 4. My Link 3’s serial starts with 7, which no firmware I looked at knows about, not even the X-T30 III. So even with perfect Bluetooth, the camera would have rejected it. The fix in linkxt is simple: treat 7 as a mini.

Step 3: Writing the missing piece

The instax Link protocol is well known thanks to people who sniffed it from the phone app: javl/InstaxBLE, linssenste/instax-link-web and others. It’s simple. Each packet starts with Ab, then a length, an opcode, a payload and a checksum. The camera asks a few questions, sends the JPEG in 900-byte chunks and says “print”.

I didn’t copy the X-S10 code. In a firmware like this, every function and every variable lives at a fixed address, chosen by the compiler when Fuji builds it. When a function calls another one, the call contains that address written in plain bytes. Change one line of code, recompile, and everything after it shifts. Two different cameras are two different builds, so the same function sits at a different address in each. Moving the X-S10 code into my camera would have meant finding and fixing hundreds of those addresses by hand. Instead, Claude and I wrote a small C module from scratch, linkxt. It sits exactly where the stubs were: the Fuji app calls it, and it calls the Fuji Bluetooth stack.

How do you plug new code into a firmware you can’t recompile? With the same fixed addresses:

  • Fuji → linkxt. The print app still calls its 12 empty functions (“send the serial request”, “send a chunk”, “print”, “connect”…) at their usual addresses. I overwrite the first 8 bytes of each one with a tiny instruction: “jump to this address”, which is the matching function in linkxt. The app has no idea; it calls the stub as always and lands in my code.
  • linkxt → Fuji. linkxt needs firmware functions too: open a Bluetooth connection, send a packet, write a file. I give the compiler a list of their addresses, found in Ghidra, and it calls them directly.
  • A few single-byte tweaks. One switches the print menu from “Wi-Fi printer” to “Bluetooth printer”, and the serial check above learns about 7.

All these patches are applied to the copy of the firmware loaded from the SD card (more on that below), never to the camera itself.

The hard constraint was space. The only safe place I found was a 4 KB hole full of zeros in the code, so linkxt had to fit in 4048 bytes. That includes a debug build with logging. Most debugging sessions started with “what can I remove to make room for this new trace?”.

Before touching the camera, every build ran in an emulator. I used Unicorn to run the real ARM binary with a fake Link 3 printer written in Python. It caught a lot of bugs at zero cost.

Step 4: Running it without flashing

Now, how do you run modified firmware without flashing it?

The answer came from jitl and the FujiMod project, found on the FujiHack Discord. Fujifilm cameras can boot from the SD card if you hold a secret button combo at power-on (on mine: Delete + press the rear dial). The card holds a tiny loader, ffinit.bin, and ffboot.bin, an image of the whole RAM (72 MB) built from the official firmware. The camera loads it into RAM and runs it. The flash is never touched.

This had been shown to work on other bodies, but nobody had tried it on an X-T30 II. Getting there took 30 trials.

Trial 1: nothing. The camera started normally. I had pressed the front dial instead of the rear one. Trial 2: green LED, black screen. That green LED was jitl’s test loader saying hello: the camera’s boot ROM had read my card. First win.

Then came a long series of black screens. The problem with booting your own code is that you have no screen, no debugger, no printf. The only thing I could control was the small LED on the back. So it became my debugger: the loader blinks green once for each stage it reaches, and goes red when something fails. I counted blinks with a stopwatch in hand.

The LED taught me a few things the hard way:

  • Patience is a feature. For several trials I thought the loader was stuck on red. It wasn’t: the ROM reads the 72 MB image sector by sector, which takes a minute and a half.
  • Emulators lie a little. One of my loaders froze silently. The C compiler had turned a byte read into a 4-byte read at an odd address. That’s fine on a normal running system, but this early in boot the processor refuses it and stops. Unicorn didn’t model that, so all my tests were green. One compiler flag fixed it.
  • Blinks don’t scale. So I taught the loader to write raw sectors on the SD card, inside a file I had created on the Mac beforehand. After a trial, I opened LOG.BIN on the Mac and read where the boot had stopped.

The log said the kernel started, but the app never did. The answer came from reading the kernel code: just before starting the app, it wipes a 128 KB log buffer. That buffer was exactly where jitl’s boot recipe (“startup”) and my own hooks lived, so they were replaced by zeros right before being used. jitl had another recipe, “cold”, that doesn’t put anything there.

Trial 30: no LED at all, then after a minute or two, a normal live view. But was it really running from the card, or had the camera given up and started from its flash? Trial 31: same card with the big image renamed. Nothing, ever. So trial 30 had really booted from the SD card.

Trial 32: my first mod. It turned the LED red for 10 seconds, then let the camera boot. Useless, and the best red LED I’ve ever seen.

(I also spent a few evenings on a USB “service mode” route that can read and write RAM live. It was great for checking my RAM image against the real thing, but useless for running code.)

Step 5: Debugging blind

Once linkxt was on the card, the camera showed a new screen: “connecting”… then “CAN NOT BE CONNECTED”. No details.

I needed logs. In the firmware, I found the function Fuji uses to write A:\UILOG\COUNTER.TXT to the SD card, and I reused it. From then on, linkxt wrote everything it did to A:\LINKXT.TXT. Each trial became the same loop:

The logs moved things forward fast:

  • Trials 34-36: scan, connect, find the instax service, enable notifications. Bluetooth works.
  • Trial 37: the first question gets an answer, but the Fuji app rejects it. The Link 3 answers in a newer layout than the old printers. A small shim in linkxt rewrites the answer.
  • Trial 38: all the questions pass and the photo upload starts.
  • Trial 39: the Link 3 accepts a print. The film counter goes from 7 to 6!

The pink ghost

Trial 39 printed. The sheet came out white and slowly developed into… an almost white picture with a faint pink boat. Not quite what I was hoping for.

Since prints cost money, I switched to “no-print” cards. They do everything, but instead of sending the JPEG they save it to the SD card and stop. The JPEG was garbage: pink, zoomed 2×, with stripes on every other column.

I first suspected my code, then the file size, then the source image (an S-size JPEG gave the same result). None of that was it. So I made linkxt dump the image buffers between each step of Fuji’s pipeline, then decoded them on the Mac.

  • After resize: a perfect image, in a YUV layout (“Y Y U V”).
  • After rotation: not YUV at all, but 32-bit ARGB pixels.

Reading the code around it explained everything. Some printers advertise a “capability bit 3”. When it’s set, the app runs an extra colour pass: YUV to ARGB, colour tweak, back to YUV. Then a copy meant for the case without the colour pass runs anyway and overwrites the clean result with half of the ARGB buffer. The encoder reads ARGB as if it were YUV, and you get a pink ghost.

It looks like a real Fujifilm bug. Maybe no printer ever set that bit for this code path, and the Link 3 is the first. The fix is one line in linkxt: hide bit 3 from the app. Trial 45, still without film, gave a clean JPEG.

It works!

Trial 46: real card, real film. Photo picked in the playback menu, “Print”, a progress bar, and the Link 3 starts whirring. A few minutes later, the boat appears.

No phone, no bridge, no flash. Pull the card and the camera is stock again.

What’s next

It’s still a debug build, and landscape photos haven’t been tested since the fix (before it, they froze on “Sending”). Next, I want to clean it up and turn linkxt into a proper FujiMod mod, so other X-T30 II owners can try it.
